# MAIN-GREEN round 4: the CLI works while the desktop app is open (no commit)

Round 3 is accepted and committed (`84aff90`, gates 63/63 and e2e 5/5). Remaining product gap from round 2: with the desktop app running, every CLI command now fails with "close the app or use another --data-dir". That's a regression in daily use; users keep the app open. The bar: **the CLI and the desktop app share one engine.**

Design (adapt to the codebase, but meet every point):
1. **Local control channel owned by the core.** When a core holds `core.lock` it also serves the existing JSON-RPC protocol on a per-user local endpoint: a Windows named pipe (`\\.\pipe\ferry-<user-scoped id>`) and a Unix domain socket inside the data dir elsewhere. No TCP port. Write the endpoint name plus a random auth token to a file in the data dir (user-only permissions, rotated each core start, removed on clean shutdown). Every connection must authenticate with the token before any method runs. Reuse the existing transport/protocol layer; don't fork the RPC surface. The e2e-only WebSocket transport stays as it is.
2. **CLI client selection:** `--engine mock` unchanged. Otherwise, if the lock is held by a live process and the endpoint file exists, connect over the channel. If the lock is free, run the in-process engine as today. If the lock is held but the channel is unreachable (older desktop version, or a crash), show a clear message naming the PID and the fix. Stale locks from dead PIDs are reclaimed (crash-resume already relies on this; keep it working).
3. **Behaviour parity:** `status`, `providers`, `run` (streaming), `resume`, `gateway start|stop|status|keys …`, `quota`, `settings` and `doctor` work over the channel, with results identical to in-process. Gateway commands act on the desktop core's gateway, so there's no second listener on the port. A long `ferry run` over the channel must survive the desktop window closing to the tray (core still alive), and must fail cleanly if the core exits.
4. **Security:** the token file is never logged. `doctor` shows the channel state without the token. Add the channel to `docs/SECURITY.md` (threat: other local users or processes; mitigations: pipe/socket ACL plus token).
5. **Tests:** unit tests for token auth (reject missing or wrong token), endpoint file lifecycle, client selection (free lock / live owner with channel / live owner without channel / stale lock), and one integration test where a CLI client drives `status` and a streaming `run` against a core started by the desktop-style host.

Typecheck, lint and prettier; tests for the orchestrator to run; no commit. Report the design as built and anything deferred.
